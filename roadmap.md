## Phase 3: Single Pane of Glass UI & Observability
- [x] Develop UI for multi-cluster namespace and resource visibility (RBAC-aware)
- [x] Implement on-demand state fetching via Dumb Agent
- [x] Settings page: server URL, agent image and agent namespace configurable at runtime instead of only through the environment
- [x] Rebuild the console UI on the Signal Deck design system: two-level rail with a live fleet list, ⌘K command palette, dark/light decks, self-hosted Inter + JetBrains Mono, and the link strand as the state device
- [x] Add Rancher-style 3rd resource navigation sidebar to Explore page (Workloads, Networking, Storage & Config, Custom Resources, Cluster)
- [x] Live utilisation from the cluster's own Metrics API (`/metrics/nodes`, `/metrics/pods`), surfaced as capacity meters on the fleet, the cluster page and the pod drawer
- [x] Log viewer controls on the streamed container log: line filter, wrap toggle, tail toggle
- [x] Resource YAML viewer and live editor — `GET|PUT /clusters/:id/resources/object` reads and replaces one object through the same impersonated tunnel, so the cluster's own RBAC decides whether a write lands and the change is audited as an `update`. Every Explore list carries per-row *View YAML* / *Edit config* actions opening a highlighted editor in the shared `Sheet`. Server-side bookkeeping (managed fields, kubectl's last-applied copy) is stripped, and a Secret is shown redacted and refused as a write — the manifest is not the whole object, so applying it would overwrite every value with its placeholder
- [x] Shell selector (`bash` / `sh`) on the pod terminal. Kubernetes takes `command` as an argv rather than a candidate list, so the previous pair of `command` parameters ran `/bin/bash /bin/sh` instead of falling back; exactly one shell is now sent, changing it opens a fresh session, and "executable file not found" names the picker as the fix
- [x] Kubeconfig generation for agent-mode clusters. An agent cluster stores no API URL and no service account token by design, so the TokenRequest path could not serve it and every attempt failed with "cluster registration is missing an API URL or service account token". Such a cluster is now issued a kubeconfig pointing at KubeMG's own proxy (`/api/v1/clusters/:id/proxy`), carrying a JWT scoped to that one cluster's proxy routes (`auth.ScopeProxy`, enforced in `RequireAuth`) so a leaked file cannot reach the rest of the API. A non-HTTPS public URL is reported as a warning rather than silently rendering a kubeconfig client-go will refuse to send a bearer token over. The kubeconfig also carries the bastion's CA in `certificate-authority-data` when the bastion is pinned, since the "cluster" kubectl dials is KubeMG itself — otherwise a self-signed bastion produces kubeconfigs that fail on x509 on the operator's laptop
- [x] Resource YAML Viewer & Live Editor: Add UI controls to view reachable K8s resources (Deployments, Pods, Services, etc.) in YAML format and configure/update them live (implemented via YamlPanel and GET/PUT /resources/object)
- [x] Multi-Shell Exec Terminal: Support both `sh` and `bash` shell options for Pod container interactive terminal sessions (implemented via PodTerminal shell picker)
- [x] Workload Lifecycle Controls (Scale & Rollout Restart) — `POST .../resources/scale` and `POST .../resources/restart` (`pkg/api/resources_actions.go`), addressing a workload by the same sidebar key every other resource call uses so the browser still never names an API path. Both are already possible on the YAML tab, and that is the point: scaling by hand-editing `spec.replicas` in a thousand-line manifest is a write of the whole object to change one integer, and asking for a rollout means knowing it is a timestamp annotation on the pod template. Neither is a new permission — both go down the same impersonated tunnel, so a `view` grant is refused by the cluster's own RBAC and both land in the audit trail as an `update`. They are **read-modify-writes rather than patches**: `Proxy.Call` sets `application/json` on any body and a JSON or strategic merge patch must arrive as `application/json-patch+json` or the API server answers 415, so each reads first and sends the `resourceVersion` back with the write, which makes the update conditional and turns a concurrent change into the API server's own 409 instead of a silent overwrite. Scale goes through the **`scale` subresource**, so what is written is four fields and a number and there is no way for it to disturb a pod template; restart has no subresource — the annotation *is* the API — so it writes the object, stripping `managedFields` the way the manifest editor does, and refuses a workload whose template is not where it should be rather than inventing one. The kinds differ per action and the table says so: a DaemonSet has no replica count (its node list is the count) and a ReplicaSet is rolled by the Deployment that owns it. Front end: `Scale` / `Restart` icon actions on every workload row and buttons on the detail drawer's footer, both opening a `WorkloadActionDialog` on the shared `Sheet` — with the scale field prefilled from what the row or the describe already read, a warning before scaling to zero or restarting something serving traffic, and a refresh of the list and the drawer on success. `Sheet` now lets only its **topmost** instance answer Escape, since the dialog opens over the drawer and one listener each on `window` would otherwise close the whole stack at once
- [x] Observability datasource registration per cluster — a cluster carries a metrics source and a logs source (`observability_sources`, one row per cluster per kind), registered from the cluster wizard's new Observability step and from the cluster page. Two access shapes: **in-cluster**, reached down the agent tunnel through the API server's Service proxy (`/api/v1/namespaces/{ns}/services/{scheme:name:port}/proxy`), so nothing is exposed and the read is impersonated and audited like any other; and **direct**, dialled from the bastion, which is what a central Thanos or hosted Mimir looks like. Credentials are stored and never serialized. Every save runs a real read against the provider's own API — not a port check — and records the verdict with the detected version, and a draft can be checked before it is saved. `GET .../observability/discover` scans the cluster's Services and offers what is already running (VictoriaMetrics, Prometheus, Thanos, Mimir, VictoriaLogs, Loki), including the path prefixes that are the usual reason a correct address 404s (`/select/0/prometheus` for vmselect, `/prometheus` for Mimir), while excluding scrape targets and write endpoints
- [x] Add dynamic CRD discovery and conditional category generation to Explore sidebar (Istio CRDs: Gateways, VirtualServices, EnvoyFilters, etc. rendered dynamically per cluster). Explore reads the open cluster's CRD list once per cluster and builds the sections that only exist because of what that cluster has installed: an **Istio** section appears when — and only when, `*.istio.io` CRDs are present, the Gateway API joins Networking where the thing it does already lives, and everything else a cluster defines lands in an **Other** section at the bottom. Because the set differs per cluster there cannot be a route per kind, so `GET .../resources/custom` names the API instead (`group`/`version`/`plural`), and `crd:{group}/{version}/{plural}` addresses one for the YAML editor. Naming an API is not reaching one: the path is *built* from three validated components rather than taken from the caller, the core group is refused so this cannot become the way around the redacting Secret handlers, and the read still goes down the impersonated tunnel with the same namespace enforcement and audit trail. A CRD uninstalled since the sidebar was built comes back `available: false`, like the Gateway API and Istio lists already do. The Istio and Other sections start collapsed, since both can run long enough to push the fixed inventory off screen. The agent manifests needed two new ClusterRoles for any of this to work through an agent tunnel — the built-in `view` role covers neither `customresourcedefinitions` nor CRD-served objects, so `kubemg-crd-discovery` and `kubemg-custom-resource-view`/`-edit` were added, with the API groups **enumerated rather than wildcarded** because `apiGroups: ["*"]` would include the core group and hand every user every Secret. Existing agent installs must re-apply to pick them up Nothing is declared twice: HTTPRoutes and VirtualServices were removed from the fixed inventory, since an entry that is always shown and usually answers "not installed" is a worse sidebar than one listing only what is there. They now live in `RICH_CRD_ITEMS` keyed by `plural.group` and are placed by discovery, carrying a *fixed* key rather than a `crd:` one so they keep their normalised hostname/gateway/rules table rather than the generic fallback — which is also the extension point for any future CRD worth a real table
- [x] Implement user-scoped persistent namespace selection across Explore sessions (retained in browser local storage). The chosen namespace is written to `kubemg_preferred_namespace` and restored whenever a cluster's namespace list is loaded, but only where it still means something: "all namespaces" always applies, a named namespace only if this cluster has it *and* the grant returned it — otherwise the page opens on the first available one. It is one preference rather than one per cluster because it is a working habit, not a property of a cluster
- [x] Helm Release Visibility & Values Management: List deployed Helm releases per cluster/namespace, view user values in YAML format, and update release values live through the impersonated agent tunnel. Helm 3 has no API and no controller — a release is a Secret labelled `owner=helm` holding the release object as base64(base64(gzip(JSON))) — so `GET .../resources/helm/releases` is that labelled secrets list read down the same impersonated tunnel, decoded server-side and deduplicated to the highest revision per release, which is the one that describes what is installed. Only chart metadata and `config` ever leave: the release object also carries the chart's rendered manifest, which for many charts holds generated passwords, and it is never in a response. Reading a release means reading a Secret, so the built-in `view` role refuses it — that is the cluster deciding, and it is the correct answer. `GET|PUT .../helm/releases/:name/values` reads and writes the supplied values as YAML; the write appends a revision the way an upgrade does (`sh.helm.release.v1.{name}.v{n+1}`, previous revision marked `superseded` in both the label Helm queries by and the payload it reads) rather than editing the current one in place, which would rewrite `helm history` and break `helm rollback`. **It renders nothing**: KubeMG has no chart to template from, so the new revision carries the previous manifest unchanged and the cluster keeps running exactly what it was running until someone runs `helm upgrade` — the backend sends that warning with every response and the drawer shows it before the first keystroke, not after the save. A release name is validated against an anchored pattern rather than escaped, because it reaches both a label selector and a Secret name; the decompression is bounded, because a Secret is capped at a megabyte but gzip expands about a thousand to one. In Explore it is a **Helm** section of its own — a release is not a workload, it is the thing that produced several of them — with *View values* / *Edit values* opening a dedicated drawer on the shared `Sheet`, since a release has no manifest of its own for the YAML editor to address
- [x] Universal Resource Detail View & Describe Engine: Expand resource drawer layout into spacious multi-tab modal (85vw/1100px) with Overview, Describe & K8s Events, YAML Editor, and Container Logs/Terminal across all Kubernetes resources. `GET .../resources/describe` addresses an object through the same fixed kind table and validated CRD components the YAML editor uses — so it adds a read, not a way to reach anything new — and returns metadata, `status.conditions`, a bounded flatten of spec and status, and **the events the cluster recorded against it**. The events are why the surface exists: a spec is what was asked for and a status says whether it happened, but only an event says *why* it did not, and KubeMG previously had no way to show them at all. It is deliberately not a per-kind describer — kubectl hand-writes one for every kind, which would be a maintenance surface out of all proportion to a drawer tab and impossible for a CRD nobody has heard of — so the three things extracted are the ones that hold for *every* object; the flatten is bounded in depth, count and value length, and says when it stopped so the YAML tab is understood as the complete view. Both Event shapes are read: an event written through `events.k8s.io` arrives on the core list with `lastTimestamp` and `count` empty and its time in `eventTime`/`series`, so reading only the legacy shape shows a cluster's newest events with no timestamp. Events are their own resource with their own RBAC, so a refusal narrows the answer (`events_available: false` with the cluster's reason) rather than failing the describe. Front end: `Sheet` gained `xl`/`2xl`/`wide` widths (the classes are a lookup, not an interpolation, since Tailwind reads the source for literal names), and the three separate drawers — pod, manifest, and nothing at all for everything else — collapsed into one `ResourceDetailDrawer` with Overview / Describe & Events / YAML / Logs & Terminal tabs, because seeing that something is not ready, asking why, and then changing it is one investigation rather than three. `PodDrawer` and `YamlDrawer` became the `PodPanels` and `YamlPanel` bodies that drawer composes; every list row now opens it from its name as well as from a *View details* action, and the YAML actions moved into the panel's own bar since the sheet footer belongs to the object rather than to whichever tab is open
- [x] Integrate VictoriaMetrics for minimal footprint metrics — the query path (`pkg/observability/metrics_query.go`, `GET .../observability/metrics/query`). The Metrics API above is a two-minute sliding window, which is why the console draws meters and never a chart; this is the same two questions asked over a window, so a pod killed an hour ago still has a shape. **The browser never sends PromQL.** A caller names a chart from a fixed catalogue (`pod_cpu`/`pod_memory`, `namespace_*`, `cluster_*`) plus namespace/pod/container, and the server writes the query around a scope resolved from their grant — because unlike every other read in KubeMG there is no cluster RBAC to delegate to: a metrics backend has never heard of the caller and answers whatever it is asked, so a namespace-scoped grant that could send its own PromQL would read the whole cluster in one line. Names are **validated, never escaped** (an anchored RFC 1123 pattern), so nothing a caller sends can become label-matcher syntax; the cluster-wide entries are refused to a scoped grant like every other cluster-wide read; the window is capped at 30 days and the step is *derived* from it, so widening a range coarsens resolution instead of enlarging the answer. NaN and ±Inf are dropped rather than serialized — Prometheus writes them for gaps and either would fail the whole JSON encode. The transport is deliberately the opposite call: an in-cluster datasource is reached as cluster-admin (its Service lives in `monitoring`, which a scoped grant does not cover), so the scope rides on the query and not on the path. Front end: `MetricsChart.tsx` draws SVG against the deck's tokens — no chart library, since the smallest one worth having outweighs the lazy-loaded terminal — with a crosshair readout, keyboard arrow-key navigation, a legend and a table view, because a chart whose values are only reachable by hovering is unreadable for half its audience. It needed the deck's **first categorical palette** (`--chart-1..8` in `index.css`): the semantic four are reserved for state, and a chart with six containers needs six identities and no state at all. Both decks are validated as sets (worst adjacent CVD ΔE 9.1 light / 8.4 dark under protanopia and deuteranopia; normal-vision floor 19.6 / 19.3) — the slot *order* is the colour-blindness mechanism, so do not reorder it and do not add a ninth. Embedded in the pod drawer's overview and on the cluster page under the datasource that answers it
- [x] Integrate VictoriaLogs/Promtail for minimal footprint logs — the query path (`pkg/observability/logs_query.go`, `GET .../observability/logs/query`). The pod log view reads live through the tunnel, which is right while the pod is there; a pod that has been replaced took its logs with it, and there was no way to ask "which pod logged this" across a namespace. The two providers share nothing but the shape that comes out, so each gets its own builder and decoder: VictoriaLogs speaks LogsQL and answers NDJSON (both the flattened `kubernetes.pod_name` key and the nested object shape are read, since reading only one shows a page with no pod names at all), Loki speaks LogQL and answers a stream envelope of `[nanoseconds, line]` pairs, asked `direction=backward` so a limited page is the newest lines rather than the oldest in the window. The scope rule is the metrics one and for the same reason. The **filter box is the one exception to validate-don't-escape**: it is the only caller value that is not a Kubernetes name — an operator searching logs has to be able to type a quote or a brace — so it is quoted as a literal, backslash-first so the escaping cannot re-escape its own output. Lines are clamped at 8 KiB and the NDJSON scanner's buffer is raised past bufio's 64 KiB default, which silently ends a scan mid-page. Front end: `LogExplorer.tsx`, wired as a third **History** stream beside Live and Terminal in the pod drawer — the two surfaces stay separate because one tails a process and the other searches a record, and they fail differently enough that merging them would make both harder to explain

Still open from the streaming work:
- [x] `port-forward` over the tunnel — carried in its WebSocket transport (`v2.portforward.k8s.io`), which the existing upgrade bridge multiplexes verbatim. The SPDY transport is still refused with a `501` that names the fix; implementing it would mean a second multiplexing protocol inside the tunnel for a transport Kubernetes is retiring
- [x] TLS in front of the bastion, so `kubectl exec` and generated kubeconfigs work at all (client-go refuses to send bearer tokens over `http://`). `KUBEMG_TLS_ENABLED` serves HTTPS from the server itself; with no certificate at `KUBEMG_TLS_CERT_FILE`/`KUBEMG_TLS_KEY_FILE` it mints a **self-signed** one covering the public URL's host plus `KUBEMG_TLS_HOSTS`, and pins that certificate into every agent install package (`bastion-ca` in the agent Secret, `KUBEMG_BASTION_CA`) so the tunnel verifies rather than skipping verification. A real certificate mounted over the same paths is used as-is and pins nothing. For a chain KubeMG cannot infer — an internal corporate PKI, or TLS terminated by an ingress in front — `KUBEMG_AGENT_CA_BUNDLE` names it explicitly and is validated at boot. **Still to do before shipping to a customer:** replace the self-signed pair with one their clients already trust, or distribute the generated `tls.crt` to every operator running `kubectl`
- [x] Audit retention policy — a background pass every 12 hours prunes past `audit_retention_days`, configurable from the Settings page
