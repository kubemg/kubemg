**Two connection modes** (`Cluster.ConnectionMode`, Phase 2): `direct` is the Phase 1 path — KubeMG stores an API URL plus a service account token and dials the cluster itself. `agent` is the bastion path — the cluster runs the Dumb Agent, which dials *out* and holds a WebSocket open, and KubeMG stores no cluster credential at all (only the registration token the agent presents). Registering in agent mode mints that token; `api_url`/`service_account_token` are required in direct mode only. `checkCluster` branches on the mode: an agent cluster's health is the tunnel pool, not a probe against an API server KubeMG has no route to. **`generateKubeconfig` branches the same way**, and must: an agent cluster has nothing to run TokenRequest against, so its kubeconfig points at KubeMG's own proxy (`{public URL}/api/v1/clusters/:id/proxy`) and carries a KubeMG JWT rather than a cluster token. That token is minted with `auth.ScopeProxy` and the cluster id, and `RequireAuth` confines a scoped token to exactly that cluster's proxy route — a kubeconfig lives on a laptop, so it must never double as a session key for the rest of the API. Revocation still works because the proxy re-reads the user and the grant on every call. The bastion's own CA is embedded in that kubeconfig's `certificate-authority-data` whenever it is pinned at all — in agent mode the "cluster" kubectl dials is KubeMG, so the CA it must trust is KubeMG's, not the target cluster's; without it a self-signed or internal-PKI bastion hands out kubeconfigs that fail on x509 at the first call. A publicly-trusted bastion embeds nothing, because pinning it would break the file at renewal. A non-HTTPS public URL comes back as a `warning` on the response instead of a kubeconfig that fails at the first call with nothing to explain it (client-go refuses to send a bearer token over `http://`).

**Phase 2 packages**: `pkg/bastion` (`server.go` tunnel listener + handshake, `registry.go` connection pool and per-tunnel request multiplexing, `proxy.go` the `kubectl` proxy, `audit.go` structured audit records, `protocol.go` the wire format, `token.go` registration tokens); `pkg/agentpkg` renders the agent install package from `base/*.yaml` embedded via `go:embed`. Routes added: `GET /agent/v1/tunnel` (agent WebSocket, authenticated by registration token, outside the JWT middleware), `GET /install/:token/{agent.yaml,kustomize.tar.gz}` (unauthenticated because kubectl cannot carry a session — the token *is* the credential), `GET /api/v1/clusters/:id/kustomize` (admin), and `ANY /api/v1/clusters/:id/proxy/*path`.

`agent/` is a **separate open-source Go module** depending only on `gorilla/websocket` — no client-go, which is what keeps the binary near 7 MB. It mirrors the wire format in `agent/internal/protocol`; the two copies agree on JSON field names and `ProtocolVersion`, which the bastion checks at handshake. The Kustomize manifests exist twice on purpose (`deploy/kustomize/base/` is human-facing, `backend/pkg/agentpkg/base/` is embedded); `make manifest-check` diffs them and is part of `make verify`, so edit both or neither.

**Known gap** (deliberate, not a bug): in **direct** mode KubeMG mints tokens but provisions no RoleBinding, so generated kubeconfigs authenticate without authorizing, and the permission matrix governs *KubeMG's own* authorization rather than the target cluster's RBAC. In **agent** mode this closes: the installed manifests bind `kubemg:view`/`kubemg:edit`/`kubemg:cluster-admin` to the built-in ClusterRoles, and the proxy asserts the caller with `Impersonate-User`/`Impersonate-Group`, so the cluster's own RBAC decides. The built-in roles have two gaps KubeMG's own manifests fill, because Explore is unusable without them: `kubemg-crd-discovery` grants read on `customresourcedefinitions` to `kubemg:users` (a definition is a schema, not the data it holds, and the sidebar is built from that list), and `kubemg-custom-resource-view`/`-edit` grant read/write on the CRD groups KubeMG surfaces first-class — Gateway API and the five Istio groups. Those groups are **enumerated, never wildcarded**: `apiGroups: ["*"]` includes the core group, and the core group is where Secrets live, so a blanket read would hand every KubeMG user every secret in the cluster. Browsing another operator's CRDs means adding its group to that ClusterRole and re-applying — the generic list and the YAML editor already work for any CRD, RBAC is the only thing in the way. **Existing agent installs must re-apply their manifests to pick these up**; until they do, discovery 403s and the sidebar simply shows no custom resources. The cluster detail page, the permissions page and the wizard's last step all say which of the two applies — keep that disclosure honest and mode-aware.

Namespace scope is enforced in the proxy (a scoped grant refuses anything not naming one of its namespaces, except discovery paths) because it is a KubeMG concept impersonation groups cannot express; the *role* is deliberately not enforced locally — that is the cluster's job, and it does it: a `view` grant really is read-only inside the cluster via the `kubemg:view` binding.

**Streaming (protocol v2)**: the tunnel carries long-lived calls as well as request/response pairs. `pkg/bastion/stream.go` multiplexes streams over the same socket by correlation ID; `streamproxy.go` has the two shapes — `serveBodyStream` for `watch` and `logs -f` (response head, then flushed chunks) and `serveUpgradeStream` for `exec`/`attach` (client WebSocket bridged to the agent's upgraded session, bytes piped verbatim because the Kubernetes channel protocol multiplexes stdin/stdout/stderr itself). Only the *handshake* is bounded (`streamOpenTimeout`); a stream itself may run for hours. A stream that its consumer cannot drain is killed alone rather than blocking the tunnel (`streamBuffer`, `ErrStreamBacklog`) — never make a full buffer block the read loop, it would stall every other stream on that socket. **`port-forward` rides `serveUpgradeStream` too**: Kubernetes offers it over SPDY *and* over WebSocket (`v2.portforward.k8s.io`), and the WebSocket shape is channel-prefixed bytes the existing bridge already carries verbatim — so it needed no wire change and no protocol bump, only routing. A SPDY client is refused with a `501` naming the fix (`KUBECTL_PORT_FORWARD_WEBSOCKETS=true`, default on 1.31+) rather than left hanging on an upgrade nobody answers; carrying SPDY would mean a second multiplexing protocol inside the tunnel for a transport Kubernetes is retiring. `offeredSubprotocols` keeps the two families apart — a port-forward negotiated as a channel protocol is a session neither end can read — and `clientUpgrader` deliberately declares **no** `Subprotocols` of its own so the client is told whatever the *cluster* agreed to; letting gorilla pick independently would answer v5 while the API server speaks v4. Bumping `ProtocolVersion` is a breaking change — the bastion refuses a mismatched handshake, so `agent/internal/protocol` must move with it.

Browsers cannot set headers on a WebSocket, so the in-page terminal authenticates with `?access_token=`; `auth.RequireAuth` accepts it **only on an upgrade request**, and `strippedQuery` removes it before the path reaches the cluster or the audit trail. Note that `kubectl exec` through the proxy needs TLS in front of the bastion: client-go refuses to send bearer tokens over `http://` at all, even to loopback. **The bastion terminates its own TLS** (`pkg/certs`, `KUBEMG_TLS_*`): with `KUBEMG_TLS_ENABLED` it serves HTTPS, and when the configured cert/key files do not exist it mints a self-signed pair covering the public URL's host, loopback and `KUBEMG_TLS_HOSTS`. Half a pair is refused rather than half-generated, and an existing certificate is never overwritten. A self-signed certificate is pinned into every rendered agent package (`agentpkg.Options.BastionCA` → the `bastion-ca` key of the agent Secret → `KUBEMG_BASTION_CA`), which the agent *adds to* the system roots rather than replacing them; a publicly-trusted certificate is deliberately **not** pinned, because pinning it would strand the fleet at renewal. `KUBEMG_AGENT_CA_BUNDLE` overrides all of that inference with the chain an operator says agents must trust, and is read **even with TLS disabled here** — behind an ingress the certificate agents verify is the ingress's, and an internal corporate PKI is not self-signed, so neither is detectable from this process's own certificate. It is validated at boot and refuses the server on a bad file: a wrong bundle strands the whole fleet with an x509 error that points at the cluster rather than at the file. The agent's `--insecure-skip-verify` equivalent for the tunnel (`KUBEMG_BASTION_INSECURE_SKIP_VERIFY`) exists for hand-running against a dev bastion and logs a warning. Booting without TLS still works for the console and warns once, naming the flag.

**Audit (`pkg/bastion/audit.go`, `storeaudit.go`, `pkg/db/audit.go`)**: every proxied call is recorded, refusals included. A streaming call is recorded **twice**, at `PhaseOpen` and `PhaseClose`, so a session that runs for an hour is visible while it is still running; the closing record carries duration and bytes each way. `VerbFor` names `exec`/`attach`/`portforward`/`log` after the subresource rather than the HTTP method — recording a shell in a production pod as a "get" would bury the most sensitive line in the trail under the most common one. Persistence is asynchronous and **drops on a full queue rather than blocking the proxy**: a slow database must never become a slow kubectl, and the structured-log auditor still has the record. `MultiAuditor` fans out to both. `GET /api/v1/audit` is readable by everyone but a non-admin is silently narrowed to their own `user_id` — do not "fix" that by making it admin-only, and do not let the query parameter widen it. Retention is enforced in the background rather than by a cron job an operator has to remember to install; see `pkg/api/audit_prune.go`.

**On-demand state (`pkg/api/resources.go` + `resources_inventory.go`)**: `/api/v1/clusters/:id/resources/*` reads live cluster state through `bastion.Proxy.Call`, which is the same impersonation, namespace enforcement and audit trail as a kubectl call — the UI gets no privileged shortcut. `resources.go` holds the plumbing (`callResource`/`decodeResource`/`fetch`, `resourceCluster`, `resourceNamespace`) plus namespaces, workloads, pods and logs; `resources_inventory.go` holds the rest of the inventory the Explore sidebar browses: `deployments`, `statefulsets`, `daemonsets`, `jobs`, `cronjobs`, `services`, `ingresses`, `httproutes`, `virtualservices`, `persistentvolumes`, `persistentvolumeclaims`, `storageclasses`, `configmaps`, `secrets`, `crds`, `nodes`. Responses are normalised server-side so the browser does not need to know fifteen Kubernetes list shapes. A namespaced list reads either one namespace or, with `?all_namespaces=true`, everything the caller may see — and those are **two different reads**, resolved by `resourceScope` into a `readScope`: an unscoped grant takes one cluster-wide path, while a namespace-scoped grant reads its granted namespaces one at a time and the results are merged (`readScope.paths`/`candidates`, capped at `maxFanOut` namespaces, sorted by namespace then name via `sortResources`). Never answer all-namespaces for a scoped grant with a cluster-wide path — it would return objects the grant does not cover, which is exactly what the proxy refuses. Three rules hold across all of them: a namespace-scoped grant is answered **from the grant** rather than by listing the cluster (so a scoped user cannot enumerate namespaces they were not given) and is refused outright on a cluster-scoped list by `requireClusterScope`, because a cluster-wide list reaches past the scope; an optional CRD (Gateway API, Istio) that answers 404 is reported as an **empty list marked `available: false`** with a reason rather than as an error, via `fetchOptional`, which also falls back across API versions; and **`configmaps`/`secrets` return keys only — no value ever enters a response**, so nothing lands in a browser cache because someone opened a list.

**Describe (`pkg/api/resources_describe.go`)**: `GET .../resources/describe` addresses an object through the *same* `objectKinds` table and `customObjectKind` components the YAML editor uses (`resourceObjectTarget` + the shared `readObject` walk), so it is a new read rather than a new way to reach anything. It returns metadata, `status.conditions`, a bounded flatten of spec and status, and **the events the cluster recorded against the object** — the events being the whole reason it exists, since a spec is what was asked for and a status says whether it happened, but only an event says why it did not. It is deliberately **not** a per-kind describer: kubectl hand-writes one per kind, which would be a maintenance surface out of all proportion here and impossible for a CRD nobody has heard of, so the three things extracted are the ones that hold for every Kubernetes object. The flatten is bounded in depth (`maxSummaryDepth`), count (`maxSummaryFields`) and value length, and reports `spec_truncated`/`status_truncated` so the YAML tab is understood as the complete view; it walks only `spec` and `status`, which is why a Secret's top-level `data` never reaches it. Both Event shapes are decoded — a legacy core `v1` Event carries `firstTimestamp`/`lastTimestamp`/`count`, while one written through `events.k8s.io` arrives on the same core list with those empty and its time in `eventTime`/`series`, so reading one shape shows a cluster's newest events with no timestamp at all. Events are their own resource with their own RBAC, so a refusal comes back as `events_available: false` with the cluster's own reason rather than failing the describe; a cluster-scoped kind's events are found by a cluster-wide list because the reporting controller picks the namespace. Ordering is newest first, unlike kubectl, because a drawer is asked what just happened and kubectl is printing a log.

**Workload actions (`pkg/api/resources_actions.go`)**: `POST .../resources/scale` and `POST .../resources/restart` are the two writes that are not worth hand-editing a manifest for, addressed by the same sidebar key every other resource call uses. They are **read-modify-writes, not patches**, and have to be: `Proxy.Call` sets `application/json` on any body, and a JSON or strategic merge patch has to arrive as `application/json-patch+json` or the API server answers 415 — so each reads the object first and sends its `resourceVersion` back with the write, which makes the update conditional and turns a concurrent change into the API server's own 409 rather than a silent overwrite. Scale goes through the **`scale` subresource**, so the body written is four fields and a number and cannot disturb a pod template; restart writes the object, because the `kubectl.kubernetes.io/restartedAt` annotation on `spec.template` *is* the API, and it strips `managedFields` like the manifest editor and refuses a workload with no template rather than inventing one. `workloadActions` is its own table rather than a flag on `objectKinds` because the two sets differ: a DaemonSet has no replica count and a ReplicaSet is rolled by its Deployment. Nothing here is a new permission — both go down the impersonated tunnel, so a `view` grant is refused by the cluster's own RBAC and both are audited. Front end: `lib/workloads.ts` owns which kind answers for which action, and `WorkloadActionDialog` is the one dialog both the workload rows and the detail drawer open; because it opens *over* the drawer, `Sheet` now lets only its topmost instance answer Escape.

**Custom resources (`pkg/api/resources_custom.go`)**: which CRDs a cluster has is a property of the *cluster*, so there cannot be a route per kind the way the fixed inventory has one. `GET .../resources/custom` names the API instead — `group`/`version`/`plural`, plus `scope=cluster` for a cluster-scoped one — and `crd:{group}/{version}/{plural}` is the resource key that addresses one object for the YAML editor (`customObjectKind` extends `objectKinds` dynamically; namespacing is decided by whether a namespace was named). Naming an API is not reaching one, and three things keep this from being an unrestricted API client: the path is **built** from three components validated against anchored patterns rather than taken from the caller, so no subresource, proxy path or query survives; the **core group is refused** (a group must contain a dot) because that is where Secrets live and their lists are served by handlers that redact first — this must never become the way around them; and the read still goes through `Proxy.Call`, so the cluster's own RBAC, the namespace enforcement and the audit trail all apply unchanged. A cluster not serving the API answers `available: false` like the optional-CRD lists, since a CRD can be uninstalled while a sidebar built from an earlier read is still on screen. What comes back is generic — a CRD's spec is whatever its author decided, so the only honest columns are name, kind, apiVersion and age; the manifest is the real view of one.

**Helm releases (`pkg/api/resources_helm.go`)**: Helm 3 has no API and no in-cluster controller — a release is a Secret labelled `owner=helm` holding the release object as base64(base64(gzip(JSON))) — so `GET .../resources/helm/releases` is that labelled secrets list read through the same `Proxy.Call`, decoded server-side and deduplicated to the **highest revision per release**, which is the one describing what is installed. Only chart metadata and `config` leave: the release object also carries the chart's rendered manifest, which for many charts holds generated passwords, and it never enters a response. Reading a release means reading a Secret, so a `view` grant is refused by the cluster's own RBAC — that is the correct answer, not a gap to close. `GET|PUT .../helm/releases/:name/values` reads and writes the supplied values (`helm get values`, not the chart defaults merged in). The write **appends** a revision the way an upgrade does — `sh.helm.release.v1.{name}.v{n+1}`, previous revision marked `superseded` in both the label Helm queries by and the payload it reads — rather than editing the current one in place, which would rewrite `helm history` and break `helm rollback`; the supersede is a full PUT because the tunnel sends one content type and a PATCH read as `application/json` is not a patch the API server accepts. **It renders nothing**: KubeMG has no chart to template from, so the new revision carries the previous manifest unchanged and the cluster keeps running what it was running until the next `helm upgrade` — `helmValuesWarning` travels with every response so a client that skips the UI is still told, and `HelmValuesDrawer` shows it before the first keystroke. A release name is **validated** against an anchored pattern rather than escaped, because it reaches both a label selector (a comma would add a term) and a Secret name; decompression is bounded at `maxHelmPayload` because a Secret is capped at a megabyte but gzip expands about a thousand to one. Front end: a **Helm** section of its own in the Explore inventory — a release is not a workload, it is what produced several of them — whose rows open `HelmValuesDrawer` (the shared `Sheet`, not `YamlDrawer`) since a release has no manifest for the object route to address.

**Observability query path (`pkg/observability/query.go`, `metrics_query.go`, `logs_query.go`; `pkg/api/observability.go`)**: `GET .../observability/{metrics,logs}/query` read *history* out of the datasource a cluster registered. This is the one read in KubeMG where authorization **cannot** be delegated to the cluster: every other call goes down the tunnel impersonated and the cluster's own RBAC answers, but a metrics or logs backend has never heard of the caller and will answer whatever it is asked. So **the browser never sends a query.** A caller names a chart from a fixed catalogue (`metricCatalogue`: pod/namespace/cluster × CPU/memory) or a set of Kubernetes names to search logs by, and the server writes the PromQL/LogsQL/LogQL around a `Scope` resolved from the caller's grant — `resolveNamespace` answers a scoped caller from their grant rather than across the cluster, and a cluster-wide chart is refused to them outright. Names are **validated against an anchored RFC 1123 pattern, never escaped**, so nothing a caller sends can become label-matcher syntax; the log *filter* is the one exception and is quoted as a literal (backslash before quote, or the escaping re-escapes its own output), because an operator searching logs must be able to type a quote. The `Window` is capped at 30 days with the step **derived** from the span, so widening a range coarsens resolution rather than enlarging the answer. NaN/±Inf are dropped in `decodeSample` — Prometheus writes them for gaps and either would fail the entire JSON encode, not just one point. The *transport* deliberately goes the other way: an in-cluster datasource is reached as cluster-admin like the probe and discovery calls, because its Service lives in `monitoring` which a scoped grant does not cover — the scope rides on the query, not on the path. Adding a chart means adding a catalogue entry, which is a line of PromQL written by someone who knows what its scope has to be. Front end: `MetricsChart.tsx` and `LogExplorer.tsx`; the chart is hand-drawn SVG (no library — the smallest one worth having outweighs the lazy-loaded terminal) and measures its container so the viewBox maps 1:1, since `preserveAspectRatio="none"` stretches axis text and turns the crosshair dots into ellipses. It introduced the deck's **only categorical palette**, `--chart-1..8`: the semantic four mean *state*, and a chart with six containers needs six identities and no state. Both decks are validated as sets (adjacent CVD ΔE 9.1 light / 8.4 dark; normal-vision floor 19.6 / 19.3) — **the slot order is the colour-blindness mechanism, so never reorder it and never add a ninth**; past eight, a chart folds the rest into one line. Every chart ships a legend, a crosshair readout, arrow-key navigation and a table view, because three light-mode slots sit below 3:1 on white and identity must never rest on colour alone.

**Live utilisation (`pkg/api/metrics.go`)**: `/api/v1/clusters/:id/metrics/{nodes,pods,pods/:pod}` read the cluster's own aggregated Metrics API (`metrics.k8s.io`, what `kubectl top` reads) through the same `Proxy.Call`, so they inherit the impersonation, the namespace scope and the audit trail — node metrics are cluster-wide and refused to a scoped grant, pod metrics fan out per namespace like every other list. metrics-server is optional, so `fetchMetrics` treats **404 and 503** as `available: false` with a reason rather than an error, the same contract the optional CRD lists use. Quantities go through `k8s.io/apimachinery/pkg/api/resource` rather than a hand parser (it is already a dependency via `pkg/k8s`; `1Gi` and `1G` differ by 7% and sub-millicore CPU rounds *up*), and everything is normalised to millicores and bytes so the browser never parses a Kubernetes quantity. This is a **live sample, not a series** — metrics-server keeps about two minutes — which is why the UI draws meters and never a chart, and why the VictoriaMetrics work is still open.

**Observability datasources (`pkg/observability`, `pkg/api/observability.go`, `pkg/db/observability.go`)**: because that sample is all the cluster keeps, a cluster that has history says where it lives. A source is stored **per cluster and per kind** (`metrics`/`logs`, one row each, `observability_sources`) rather than server-wide — two clusters have two Prometheuses. Two access shapes exist and they are genuinely different: `in-cluster` is reached down the agent tunnel by asking the API server to proxy to a Service (`/api/v1/namespaces/{ns}/services/{scheme:name:port}/proxy{prefix}{path}`), so nothing has to be exposed and the read is impersonated and audited like every other; `direct` is dialled from the bastion, which is the shape a central Thanos or a hosted Mimir takes. An in-cluster source on a direct-mode cluster is refused (409) rather than stored unreachable, and a credential on an in-cluster source is flagged as pointless — the API server makes the onward call, so there is nowhere to put the header. The credential is treated like a cluster's service account token: stored, never serialized, and **omitting it on an edit keeps the stored one** so changing a port does not mean re-typing a token. Every save runs `observability.Probe`, which is a real read of the provider's own API (`/api/v1/query?query=1` for the Prometheus-compatible four, LogsQL for VictoriaLogs, `/loki/api/v1/labels` for Loki) rather than a port check — something listening is not the backend anyone configured — and records status, message and detected version; a 404 is explained as a path-prefix problem instead of being reported as unreachable. `POST .../sources/:kind/test` checks a **draft nobody has saved**, which is what makes the wizard's check honest. `GET .../observability/discover` reads Services through the same tunnel and offers what the cluster is already running, carrying the prefixes that are the usual reason a correct address 404s (`/select/0/prometheus` for vmselect, `/prometheus` for Mimir) and excluding scrape targets and write endpoints (a node-exporter answers on `/metrics` and would look alive while returning nothing anyone asked for). Reading the configuration is open to anyone the cluster is granted to — you cannot be shown a chart from a source you may not know exists — while writing it is admin-only. Routes are grouped as `/api/v1/clusters/:id/observability` (GET), `.../observability/sources/:kind` (PUT/DELETE), `.../sources/:kind/{test,check}` and `.../observability/discover`; the `sources` segment exists because gin cannot have a static and a param child at the same level. Front end: `lib/datasources.ts` is the single source of truth for providers, default ports and prefixes, and `components/DatasourcePanel.tsx` holds both the cluster-page panel and the editing `Sheet`, reused verbatim as the wizard's fourth step.

## Product Architecture (from PROJECT_KNOWLEDGE.md)
KubeMG is a centralized, web-based Kubernetes access/management platform (alternative to Rancher/K8s Dashboard/Lens), commercial closed-source with an open-source agent component:
- **Bastion/Gateway Proxy**: central server proxies all K8s API traffic over port 443, inspecting `kubectl` commands (including `exec`/`logs`) and keeping audit logs. Developers never get direct network access to the K8s API or nodes.
- **Dumb Agent**: a lightweight (~10-15 MB) open-source agent deployed in-cluster that opens an *outbound* reverse tunnel (gRPC/WebSocket) to the central server — no inbound firewall ports needed, no heavy in-cluster CRDs/controllers.
- **K8s Impersonation**: the proxy talks to the K8s API using `Impersonate-User`/`Impersonate-Group` headers instead of managing per-user Service Account tokens.
- **Kubeconfig issuance**: short-lived `kubeconfig`s are generated via the K8s TokenRequest API (MVP/Phase 1).
- **Observability isolation**: live pod state is fetched on-demand via the Dumb Agent; metrics/logs use either the customer's existing stack (BYO Prometheus/Loki/Elastic) or an auto-provisioned lightweight VictoriaMetrics + VictoriaLogs/Promtail stack — avoid heavy monitoring tooling.
- **Licensing model**: backend (Go/Rust) + UI + identity/authz are closed-source with license keys (SaaS or on-prem); only the Dumb Agent is open-source.

See `roadmap.md` for the phase breakdown (Phase 1 MVP → Phase 2 Bastion/Agent → Phase 3 Single Pane of Glass UI/Observability → Phase 4 Enterprise SSO & Federation) and current checkbox status — always check it before starting work to confirm what's already done.

## Containerized Commands (Docker execution)

All building, testing, dependency management, and dev server tasks must be run inside Docker containers.

**Preferred entrypoint: the root `Makefile`** (wraps every command below in a container, with cached Go module/build and npm volumes). Run from project root:
```bash
make verify           # manifest-check + backend vet/test/build + agent vet/test/build + frontend lint/build
make test             # backend + agent tests
make build            # backend + agent + frontend build
make manifest-check   # diff deploy/kustomize/base against the embedded copy
make backend-test     # go test ./...
make backend-vet      # go vet ./...
make backend-build    # go build -o server ./cmd/server
make backend-tidy     # go mod tidy
make agent-test / agent-vet / agent-build / agent-tidy   # the open-source agent module
make agent-image      # distroless agent image (AGENT_VERSION=x.y.z)
make frontend-lint    # oxlint
make frontend-build   # tsc -b && vite build
make up / down / logs / ps   # docker compose dev stack (backend :8080, frontend :5173)
```

`docker-compose.ci.yml` exposes the same jobs as compose services for CI runners:
```bash
docker compose -f docker-compose.ci.yml run --rm backend-test
docker compose -f docker-compose.ci.yml run --rm frontend-build
```

Raw equivalents — backend (run from project root):
```bash
# build server binary inside container
docker run --rm -v $(pwd)/backend:/app -w /app golang:1.26 go build -o server ./cmd/server

# run all tests
docker run --rm -v $(pwd)/backend:/app -w /app golang:1.26 go test ./...

# run single test
docker run --rm -v $(pwd)/backend:/app -w /app golang:1.26 go test -run TestName ./pkg/auth

# tidy go modules
docker run --rm -v $(pwd)/backend:/app -w /app golang:1.26 go mod tidy
```

Frontend (run from project root):
```bash
# install dependencies
docker run --rm -v $(pwd)/frontend:/app -w /app node:22 npm install

# run dev server on :5173
docker run --rm -v $(pwd)/frontend:/app -w /app -p 5173:5173 node:22 npm run dev -- --host

# build frontend (tsc & vite build)
docker run --rm -v $(pwd)/frontend:/app -w /app node:22 npm run build

# lint frontend
docker run --rm -v $(pwd)/frontend:/app -w /app node:22 npm run lint
```

**Toolchain Note**: Host installation of Go, Node, or npm is not required. All tools are executed strictly within disposable Docker containers.
